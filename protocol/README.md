# Протокол проверяемого инференса

Реализация начата 13 октября. Здесь будет код, которым сеть проверяет,
что исполнитель считал на той модели, за которую ему платят.

Замеры, на которых всё стоит, — в
[`research/inference-determinism/`](../research/inference-determinism/README.md).
План по шагам — в документе по ИИ-вычислениям. Этот каталог закрывает
шаги 10–11 плана: правило проверки и его вердикт.

Запуск:

```sh

docker run --rm -v "$PWD/protocol/contract:/w" -w /w rust:slim cargo test

```

Тест не выдумывает данные. Он берёт сохранённые векторы вероятностей из
`results/phase4/` и `results/crosscard/` и требует, чтобы правило дало на
них те же числа, что опубликованы: честное среднее 0,01270, худшее
честное 0,04466, минимум подлога 0,03778. Выдуманные векторы проверили бы
арифметику и пропустили ошибку в постановке — ровно ту, на которой
сгорела фаза 2, где сравнивались хвосты двух разных распределений.

## Правило

```
расхождение = среднее |Δ logprob| по общей длине векторов
порог       = 0,0360
проверок    = 4, у разных проверяющих
виновен     = все четыре превысили порог
```

| Величина | Откуда |
|---|---|
| Порог **0,0360** | между 99,74-м процентилем честного и минимумом подлога (0,03778) |
| **Четыре** проверки | двух не хватает: при 2,14 млн ответов в сутки доля 6,9·10⁻⁶ даёт 15 ложных обвинений в сутки на карту; четыре дают 0,04 в год |
| «**Все** превысили» | подлог превышает порог в 100% случаев, честный в 0,26%; при таком соотношении «хотя бы одна» только добавляет ложных обвинений |
| **Среднее**, не максимум | максимум шумит там же, где честная пачка, и дважды давал ложный вердикт (фаза 1) |
| Минимум **32 токена** | ниже запас падает до 1,6× |

## Чего правило не делает

**Не проверяет короткие ответы.** Ниже 32 токенов способ не работает, и
такие задания на проверку не отправляются. Жулик, обслуживающий только
короткий недвусмысленный поток, этим правилом не пойман — это свойство
признака, а не недоработка.

**Не работает на другой модели или версии рантайма.** Порог измерен для
`Qwen2.5-7B-Instruct` на vLLM 0.31.0 в bfloat16 и действителен только для
этой связки. `check_eligible` отклоняет всё остальное: обновление
рантайма обнуляет порог до перезамера, и это должно быть параметром
консенсуса, а не договорённостью между людьми.

**Не судит по одному расхождению разной длины.** Векторы разной длины
сравниваются по общей части: жадное декодирование может оборваться по
лимиту токенов в разный момент, и это не подлог.

## Контракт

Шаг 7 сделан: `contract/` — реестр исполнителей, жизненный цикл задания,
сбор проверок и вердикт. Денег в нём нет вовсе, это шаг 14.

```sh
# тесты
docker run --rm -v "$PWD/protocol/contract:/w" -w /w rust:slim cargo test

# артефакт для загрузки в цепочку
docker run --rm -v "$PWD/protocol/contract:/code"   -v registry_cache:/usr/local/cargo/registry   cosmwasm/optimizer:0.16.0
```

Собранный wasm — 273 116 байт, сумма
`13a90d5959674cefaeccb261804951b1c39c1ee8f5090614211b824d6a7c2170`.
Из возможностей цепочки требует только `iterator`, а он у Axiome есть, —
то есть загрузится. Это проверено по экспортам `requires_*` в самом wasm,
а не предположено.

**CosmWasm 1.x, не 2.x.** У Axiome wasmd v0.50.0 с wasmvm 1.5.0 и набор
`cosmwasm_1_1..1_4`; возможности `cosmwasm_2_0` там нет, и контракт на
2.x цепочка отвергнет при загрузке.

**Две зависимости прижаты** (`base64ct`, `zeroize`): свежие версии требуют
edition2024, которого нет в Rust 1.78 внутри штатного сборщика. Без этого
проект собирается локально и падает именно там, где делается артефакт для
цепочки. `Cargo.lock` поэтому в репозитории — иначе сумма сборки
невоспроизводима.

### Что в контракте уже решено

**Допуск подтверждает `attestor`, адрес из настроек.** Это не лень, а
ограничение площадки: контракт **не может** прочитать `x/referral`,
потому что у Axiome из набора возможностей wasm вырезан `stargate`.
Значит статус проверяет кто-то вне контракта и сообщает результат внутрь.
Ограничение видно в коде, а не спрятано в договорённости.

**Расхождение в микродолях** (1e-6), не в плавающей точке: её на цепочке
нет, а будь она — разные узлы давали бы разный результат. Порог 0,0360 это
36 000; между худшим честным и минимумом подлога 6 880 микродолей, так что
разрешения хватает с запасом.

**Бан необратим.** Ни `attestor`, ни админ не возвращают пойманного на
подлоге — иначе наказание ничего не стоит. Это проверено тестом.

### Спор: кто проверяет проверяющих

Шаги 8 и 9 сделаны. Дыру оставлял `SubmitCheck`: проверяющий сообщал
расхождение числом, и оспорить его было нечем — его слово против слова
исполнителя.

Теперь проверяющий **обязуется хэшем своего вектора** вместе с числом, а
`ResolveDispute` раскрывает оба вектора, сверяет их с обязательствами и
**пересчитывает расхождение в контракте**. Заявленное не совпало с
пересчитанным — проверяющий помечен нечестным.

Вызвать разбор может кто угодно: исход определяют сами векторы, поэтому
не нужно ни залога спорщика, ни права на спор. Разбирается **до**
`Finalize` — после сведения вердикт уже применён.

Чтобы пересчёт был возможен на цепочке, вектор хранится целыми числами:
`MicroLog` это logprob в микродолях со знаком (−0,693147 → −693_147).
Канон хэша — каждый элемент как i64 little-endian, восемь байт, подряд,
без длины и разделителей. Представление должно быть единственным, иначе
два честных узла получат разные хэши от одного вектора; **демоны обязаны
кодировать так же**.

Деление при усреднении целочисленное, вниз — округление работает в пользу
исполнителя, и это правильнее обратного: лучше пропустить на границе, чем
обвинить честного.

Денomы расчёта и залога (`settlement_denom`, `stake_denom`) заведены
строками в настройках. Денег в контракте по-прежнему нет, поля заранее —
чтобы имя токена не просочилось в логику по дороге. На Axiome расчётный
BARTR это контракт CW20, а при появлении IBC расчёт переедет на ваучер,
то есть на **другой** денom; это должно быть правкой настройки, а не
выпуском нового контракта.

## Демоны

Шаг 10 сделан: `daemon/`.

```sh
python protocol/daemon/test_canon.py     # канон против цепочки
python protocol/daemon/test_daemons.py   # логика демонов
```

| Файл | |
|---|---|
| `canon.py` | кодирование, хэш, пересчёт — обязаны совпадать с контрактом |
| `chain.py` | параметры протокола из настроек контракта |
| `vllm.py` | клиент с прибитыми параметрами плюс `self_check` |
| `executor.py` | породить ответ и обязаться вектором |
| `checker.py` | оценить ту же пару и обязаться своим |

### Канон сверен с цепочкой, а не написан заново

`test_canon.py` держит **шесть эталонных хэшей, снятых с реализации на
Rust**. Rust здесь авторитет: он работает на цепочке. Те же значения
продублированы её собственным тестом — разойдётся любая из двух
реализаций, упадёт её тест.

Это не формальность: при расхождении кодирования честный исполнитель
окажется обвинён, а его раскрытие — отвергнуто.

**Ловушка, закрытая отдельно.** Пустой вектор даёт
`e3b0c442…b855` — sha256 пустой строки. Это осмысленный хэш, и сам по
себе он ничего не ловит; ровно этой суммой подписывались две пустые
выгрузки состояния, которые я принял за успешные репетиции отката.
Пустоту проверяет `require_nonempty`, а контракт отвергает её при
пересчёте.

### Узел проверяет себя до работы

`self_check` гоняет один запрос дважды и требует **побитово одинаковый**
ответ. Не совпало — префикс-кеш не отключён либо включена выборка, и
участвовать нельзя: порог для такого узла недействителен. Оба демона
отказываются работать, а не предупреждают.

### Проверяющий отказывается от чужого вектора

Вектор исполнителя живёт вне цепочки, в цепочке только его хэш. Поэтому
`checker.py` **первым делом сверяет полученный вектор с обязательством** и
отказывается считать, если он не тот: иначе расхождение вышло бы про
чужие данные и обвинило честного.

### Чего в демонах нет

**Отправки в цепочку.** Демоны собирают готовый JSON сообщения и
печатают его; отправка — делом вызывающего (`axmd tx wasm execute`). Так
они проверяемы без живой цепочки, и это осознанный выбор, а не
недоделка.

**Передачи вектора проверяющим.** Исполнитель кладёт вектор в файл,
проверяющий читает файл. Чем это будет в работе — отдельный вопрос
доступности данных, и он не решён.

### Параметры живут в цепочке, а узел с ними сверяется

Шаг 12 сделан, и он не про перенос константы. Дыра была такая:
исполнитель при регистрации версию рантайма только **заявляет**, и до
этого шага заявленное с действительным никто не сверял. Обновил он
vLLM — порог для него молча перестал быть действительным, а сеть об этом
не знает.

Теперь `chain.py` читает порог, число проверок, минимальную длину и
связку модель/рантайм/dtype **из настроек контракта**, а демон спрашивает
версию **у самого сервера** (`/version`) и отказывается работать при
расхождении. Неполные настройки — отказ, а не умолчание: умолчание
означало бы, что демон живёт по своему представлению о протоколе.

Версию определить не удалось — тоже отказ, а не предположение. Маршрут
`/version` существует, но формат его ответа в документации vLLM не
описан, поэтому разбор терпимый и при любой неожидаемости бросает
`VersionUnknown`.

Приведение версии (`0.31.0` → `vllm-0.31.0`) сделано **в одном месте**:
если каждый демон будет приводить по-своему, они разойдутся в том, что
считать совпадением.

В `verify.py` константы связки остались, но переименованы в
`MEASURED_*`. Это запись о том, **при чём мерили**, а не источник истины
для протокола.

### Проба на эталонном векторе: связка сверяется по поведению

Сверка связки по **именам** оказалась недостаточной, и это замер, а не
рассуждение. На одной и той же карте, с той же моделью, той же версией
vLLM и тем же dtype, `--enforce-eager` против пути по умолчанию дал:

* ни одного побитово совпавшего вектора из 40;
* среднее расхождение **49 424** микродолей — внутри полосы подлога
  (минимум подлога FP8 37 780);
* максимум по текстам **413 488**.

То есть честный узел в неверном режиме исполнения выглядит жуликом, а
все три заявленных имени у него правильные. Сверять имена значит
проверять то, что узел о себе **сказал**.

Поэтому связка проверяется ещё и по поведению. В настройках контракта
лежит обязательство эталонным набором (хэш склейки эталонных векторов),
границы текстов и предел. Сами векторы вне цепочки — 3 948 чисел, — тем
же приёмом, что и вектор задания; эталон лежит в
`daemon/probe/probe.json` и **сверяется с обязательством из цепочки**
перед работой, иначе подменённый файл давал бы любую пробу.

Узел оценивает те же тексты, считает расхождение с эталоном и публикует
максимум вместе с обязательством **своими** векторами
(`SubmitConformance`). Соврать можно — расхождение он считает сам, — но
обязательство делает ложь опровержимой: любой раскрывает оба набора
(`DisputeConformance`), контракт пересчитывает и банит совравшего. В
отличие от спора по заданию, здесь нет ничьей оценки: оба набора
зафиксированы хэшами, пересчёт однозначен — потому и наказание прямое.

**Статистика — максимум по текстам, а не среднее по склейке.** Неверный
режим портит **редкие** тексты: у eager 29 векторов из 40 совпали с
собой побитово, а остальные разошлись до 413 488. Среднее по склейке
такую порчу размывает — замерено, что зазор падает с 20x до 1,5x, и
жулик пробу проходит. Максимум по текстам даёт честные 20 137 против
413 488.

**Предел 60 000, и он выведен из данных.** Честные максимумы по текстам:
A100 против 4090 — 19 656, 3090 против 4090 — 20 137, **другой 4090
против этого же эталона — 22 421**. Неверный режим исполнения — 410 012,
три текста выше 118 000.

Третье наблюдение, снятое 14 октября на живом прогоне, и заставило
предел поднять. Прежние 25 000 оставляли запас **1,1x** к худшему
честному наблюдению: честная карта той же модели прошла бы на волосок, а
четвёртая могла бы получить отказ. 60 000 дают запас 2,7x, и неверный
режим всё равно превышает предел в 6,8 раза, на четырёх текстах из
тридцати четырёх — обнаружение не ослабло. Выше 100 000 поднимать нельзя:
там обнаружение начинает падать.

Требовать одинаковых карт не нужно и неверно: межкарточное честное
расхождение (13 297 в среднем) сошлось с внутрикарточным (12 700). А вот
«та же модель карты» запаса НЕ даёт — два 4090 разошлись сильнее, чем
4090 с A100.

**Проба требуется и от проверяющего.** Его завышенное расхождение — это
не подлог исполнителя, а ложное обвинение честного, и правило «виновен,
если превысили все» от этого не спасает: четыре неверно настроенных
проверяющих вынесут вердикт согласованно. Цена решения: проверять теперь
может не кто угодно, а зарегистрированный и прошедший пробу узел.
Залога с проверяющего по-прежнему не требуется.

**Смена эталона или связки обнуляет все пробы** через
`conformance_version`: проба свидетельствует о соответствии конкретной
настройке, после её смены свидетельство пустое. Правка настроек, не
меняющая связку, пробы не обнуляет — иначе любая правка выбивала бы из
работы всю сеть.

**Чего проба не знает:** карт, кроме трёх замеренных. Узел на H100
может честно разойтись сильнее предела. Поэтому предел — параметр
цепочки, а не константа в коде.

### Деньги

Шаг 14 сделан. **Залог в AXM (нативный). Расчёт — выбор настройки:
родная монета либо CW20.**

```
settlement: {"native": "uaxm"}   либо   {"cw20": "axm1…"}
```

Выбор, а не два контракта, по той же причине, что и шаг 8: при появлении
IBC расчёт переедет на ваучер — то есть на третью единицу, — и это должно
быть правкой настройки, а не выпуском нового контракта. Переключение
проверено тестом: после смены настройки принимается родной платёж, а CW20
отвергается.

**Родной расчёт** добавлен 14 октября, потому что шлюз этапа 1 собирает
AXM. Разные монеты на двух этапах пришлось бы объяснять каждому владельцу
карты, а BARTR для выплат слаб: выпуск разрешает сервер без предела, 40%
лежит на одном адресе, и сжигание — не стока, а заявка на выкуп через
развязку.

При родном расчёте платёж приходит **с транзакцией**: `SubmitJob` с
монетой. Принимается ровно одна монета ровно того денoma — чужая рядом с
нужной отвергается, потому что осталась бы в контракте навсегда: вернуть
её некому и нечем. Выплаты идут `BankMsg::Send`.

При расчёте CW20 платёж приходит только через `Receive`, и вызов обязан
прийти от контракта расчётной единицы — иначе любой объявил бы задание
оплаченным своим токеном. Это цена того, что единица не нативна.

Оба пути закрыты друг от друга: родной платёж при расчёте CW20
отвергается, и наоборот. Два пути для одних денег — это две дыры вместо
одной двери.

**Доказано на цепочке, а не только в тестах.** Девнет разворачивает
второй реестр с родным расчётом: задание оплачивается одной транзакцией,
проверяющий получает ровно свои 24 250 родной монетой, а на контракте
остаётся только залог — то есть цена разошлась без остатка. Выплата
проверяется по ТИПУ сообщения, а не по отладочной строке: строка это
представление, и меняется она не вместе с поведением.

| | |
|---|---|
| Залог | `DepositStake` нативными, не ниже `min_stake` |
| Проверка залога | при **взятии** задания, а не только при допуске |
| Возврат залога | нельзя забаненному и нельзя при незакрытых заданиях |
| Проверяющим | доля от цены, **независимо от вердикта** |
| Исполнителю | цена минус плата проверяющим, если чист |
| Заказчику | возврат, если исполнитель виновен |
| Конфискат | сжечь либо по адресу — **никогда обвинявшим** |

**Решение, которое я не принял за вас.** Замер говорит: четыре проверки
стоят 9,7% от порождения. Но **кто их платит** — заказчик, исполнитель
или сеть — это выбор, а не измерение. Поэтому `verifier_fee_bps` в
настройках, а 970 bps в тестах стоят как замеренная величина, не как
решение.

**Проверяющим платят при любом вердикте — и это не щедрость.** Плати им
из исхода, появится интерес к исходу. Ложное обвинение честного у нас
4,8·10⁻¹¹ на проверку, то есть случайно этого не бывает; но сговор это
другая угроза, и платить обвинявшим из конфиската значило бы создать её
своими руками. Им платят за то, что проверка **состоялась**.

Варианта «конфискат проверяющим» в типе `Forfeit` **нет вовсе** — не
отключён настройкой, а отсутствует.

Остаток от целочисленного деления платы остаётся на контракте, а не
достаётся кому-то по случайности.

**Оговорка, которую я не могу снять.** `Forfeit::Burn` опирается на
`BankMsg::Burn`, а он требует поддержки от цепочки. Против Axiome это не
проверено — там нет живого доступа. Поэтому второй вариант
(`ToAddress`) оставлен не для красоты: если сжигание не работает,
конфискат настройкой уводится в пул или заказчику.
